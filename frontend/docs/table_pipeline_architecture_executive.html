Multi-Store RAG Chatbot · Table Pipeline · Executive Overview

Turning PDF tables into answers you can trust

Multi-Store RAG Chatbot reads tables out of documents — even when a single table spans several pages or has merged cells — and lets users ask questions two ways: in plain language, and as exact calculations. Every answer is traceable back to the page it came from.

Verified live end-to-end · 667 tests passing · commit f36454d · 2026-07-03
What it does

Four capabilities, one pipeline

Each capability closes a real gap that would otherwise produce silently wrong or incomplete answers to business questions.

🔗

Multi-page tables

A table split across pages is re-assembled into one logical table before it's stored.

Why: otherwise "sum the whole table" only sees one page.
▦

Merged cells & headers

Rowspan/colspan and multi-row headers are captured structurally, not flattened away.

Why: a 2-row header was previously misread as data, corrupting counts.
Σ

Exact calculations

SUM / AVG / COUNT / MIN / MAX and exact lookups run on the real numbers, not an AI estimate.

Why: language models approximate; finance needs exact.
⛓

Full traceability

Every stored value traces back to its source page, image, and document.

Why: answers must be auditable, with page citations.
System flow

From uploaded PDF to a cited answer

A document is parsed, understood, stored with full lineage, then answered from two directions at once — semantic search and exact computation.

The pipeline at a glance — understand, verify, store, then answer two ways.
The key ideaSemantic search answers "what does this say?" Exact computation answers "what is the total?" Running both and citing sources gives answers that are both fluent and correct — the gap most document-AI systems leave open.
In business terms

What this means for the people asking questions

Accuracy"Is the total it gives me actually correct?"
Yes — aggregate questions are computed on the real stored numbers, then verified against the database. A live SUM returned 1,062,740.0, matched exactly by an independent recount.
Completeness"If a table spans 3 pages, do I get all of it?"
Yes — the three page-fragments are merged into one logical table (70 rows) before anything is stored or answered.
Trust"Can I see where an answer came from?"
Every answer carries page citations, including page ranges when the source spans a boundary. Lineage is traceable from the PDF all the way to the cited chunk.
Safety"What if something goes wrong silently?"
Four automated gates block a document from being marked "complete" if its data is inconsistent — a silent-corruption failure mode was found and closed during validation.
Built-in safeguards

Four gates that stop wrong data reaching users

Correctness isn't assumed — it's checked. A document that fails any gate is flagged, not silently marked complete.

The count check was added after validation caught a real silent-corruption incident — see below.
A real incident, caught and closedDuring validation, a leftover background process running old code silently produced broken results half the time — while still reporting success. The count-check gate plus version-stamping now catch this class of failure before any user sees it, and record exactly which process was responsible.

Honest limits

What it deliberately does not do (yet)

Stated plainly so there are no surprises in a technical review. None of these are bugs — they're scoped boundaries.

PDF-first

Multi-page table merging works for PDFs; Word/PowerPoint/Excel tables aren't merged across pages yet.

One table per calculation

Exact math runs over a single best-matching table, not across multiple tables at once.

Rare merge false-positive

Two unrelated tables with identical column headers on back-to-back pages could be merged. Uncommon; documented.

Answer wording

The underlying data and citations are correct; occasional phrasing quality depends on the language model, tracked separately.
