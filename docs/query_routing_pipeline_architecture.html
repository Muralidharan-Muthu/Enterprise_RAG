Overview

Two pipelines, one schema

Documents flow in through ingestion, get classified and split into one of four specialised Postgres/pgvector stores. Chat queries flow through a separate query pipeline that embeds the question, decides which of those stores are worth searching, retrieves and reranks candidates, and hands the result to Gemma 4 to write the answer.

This document walks the query pipeline in the order it actually executes, then covers the ingestion side and the optional agentic/GraphRAG layers that can sit on top of it.

System architecture

Ingestion and query meet at one shared store layer

The two pipelines never talk to each other directly — they only share the Postgres/pgvector schema in the middle. Ingestion is the only writer; the query path is the only reader. That separation is why routing (Step 02) matters: the query side has no way to know what's inside a store except by asking it.

Ingestion

How a document becomes searchable

A Celery task (ingestion_orchestrator.py) runs five sequential stages per uploaded file, tracked in ingestion_jobs:

1

Parsing

Docling extracts text, tables, and images (OCR + table structure) into a ParsedDocument. OCR dominates cost — roughly 180s for a 5-page image/table-heavy PDF on CPU.

2

Routing

Gemma 4 (CDAC endpoint) classifies the document into policy / financial / legal / research, falling back to rule-based classification if the endpoint is unavailable.

3

Chunking

A type-aware, semantic-breakpoint splitter (LlamaIndex-style; top-5% dissimilarity percentile) divides the document. Legal documents additionally run extract_legal_clauses() as a separate pass.

4

Embedding

BAAI/bge-large-en-v1.5 (1024-dim) embeds every chunk; financial table summaries are embedded separately from their surrounding narrative text.

5

Storing

storage_service.store_chunks() routes each chunk into its destination store by document type — see the map below.

Document type → destination store
Document typePrimary storeNotes
vectorpolicy documentsSemantic chunks, HNSW index
table + vectorfinancial documentsTables as JSON + markdown; narrative text chunked separately
clauselegal documentsClause-level rows with risk_level, parties, key_dates (JSONB)
researchresearch documentsChunks carry citation metadata

All four stores live in the multi_store_rag_working Postgres/pgvector schema. A fifth store, image_store, holds extracted images as a pure repository — it has no embedding column and is never searched directly; searchable image-derived content (tables, clause text, prose) is cross-stored into the four stores above by a VLM-driven router (store_router.py).

Query pipeline · Step 01

Embed the query

The raw query string is embedded once, up front, with the same BAAI/bge-large-en-v1.5 model used at ingestion — but with a retrieval-specific instruction prefix BGE requires for asymmetric search.

# embedding_service.py
QUERY_PREFIX = "Represent this question for searching relevant passages: "
embedding = model.encode(QUERY_PREFIX + query, normalize_embeddings=True)

The resulting 1024-dim, L2-normalized vector is used three times downstream: for the store-routing decision (Step 02), for the HNSW similarity search itself (Step 03), and — optionally, if RETRIEVAL_CACHE_ENABLED is on — it's cached in-process for up to 6 hours so an identical repeated query skips re-embedding entirely.

Query pipeline · Step 02 — the centerpiece

Route the query to the right stores

Before any database is touched, intent_service.classify_intent() decides which of the four searchable stores are worth querying. It escalates through three tiers — cheapest first — and stops at the first one that produces a confident answer. Every tier that fails open still leaves the query recall-safe: an ambiguous query searches every store rather than guessing wrong.

01instant

Rule-based keywords

_rule_based_intent() matches the query text against six keyword sets (table, legal, financial, research, visual, policy) and maps each hit to its minimal store set. One category match → high confidence; several → medium; none → ambiguous.

confidence ≥0.80→return immediately, skip tiers 2 & 3
02~free

Semantic router

semantic_router.classify() compares the query embedding from Step 01 — reused, not recomputed — against four precomputed centroid vectors, one per store, each averaged from a handful of representative prototype phrases. Cosine similarity is a plain dot product since every vector is already L2-normalized. Catches paraphrases the keyword list misses, at the cost of a few dot products.

semantic confidence > rule confidence→return semantic result
03network

Gemma 4 (LLM)

A full round-trip to the CDAC Gemma 4 endpoint with a store-classification system prompt, returning strict JSON (stores, doc_types, confidence, reasoning). Off by default — INTENT_USE_LLM=False — because it adds real latency to the query's critical path; reserved for deployments where routing precision matters more than speed.

parses & INTENT_USE_LLM on→return parsed result
↺

Recall-safe fallback

If nothing above resolved confidently, the rule-based result from tier 1 is returned as-is — which, for a truly ambiguous query, already means all four stores at confidence 0.4.

The final gate: is the routing decision trusted at all?

Whichever tier wins, retriever_service._select_stores() applies one more check before trusting it. Below INTENT_CONFIDENCE_THRESHOLD, the narrowed store set is discarded and every store is searched — the router can only ever narrow for speed, never narrow incorrectly and lose results.

Query pipeline · Step 03

Retrieve from the selected stores

Every store flagged "in" by Step 02 runs an HNSW approximate-nearest-neighbor search in parallel against its own embedding column, returning up to 10 candidates per store on the classic path (the module-level default is 15, used by the agentic path and hybrid_retrieve()'s own default).

  • Table filters — an optional structured prefilter (currency, fiscal year, table category, numeric-only, minimum extraction quality) narrows table_store before the vector search runs, not after.
  • Hybrid mode (HYBRID_IN_CLASSIC_PATH, off by default) — fuses this semantic pass with a parallel full-text keyword search (Postgres tsvector/GIN) via Reciprocal Rank Fusion, so exact-term matches surface even when embeddings miss them.
  • GraphRAG expansion (GRAPHRAG_ENABLED, off by default) — for un-pinned queries, a lightweight router decides global (map-reduce over community summaries), local (entity-neighborhood expansion, 1 hop), or none, and merges any extra chunks in before reranking.
Query pipeline · Step 04

Balance the pool, then rerank

Raw ANN results are capped at 8 per store (RERANK_PER_STORE_CAP) before ranking — so one chatty store can't crowd out the others purely by volume.

The balanced pool (≤40 candidates, MAX_RERANK_CANDIDATES) is scored by BAAI/bge-reranker-large, a cross-encoder that sees the query and each chunk together rather than comparing independent embeddings. Raw logits are converted to a usable [0,1] score with a blended formula, because a plain sigmoid made genuinely correct matches read as ~18% confident:

final_score = 0.3 × sigmoid(logit) + 0.7 × minmax(logit within this batch)

If the reranker errors, results fall back to Reciprocal Rank Fusion (rrf_merge) over the raw distance order rather than failing the request.

Query pipeline · Step 05 · optional

Exact structured facts, alongside semantic retrieval

When STRUCTURED_QUERY_ENABLED is on (default), table_query_engine.try_structured_query() runs in parallel with the steps above — never instead of them. If the query is recognized as an exact aggregate (SUM/AVG/COUNT/MIN/MAX) or a specific row/column lookup, it computes the answer directly from table_store.json_data and prefixes it to the synthesis prompt as an authoritative fact:

"Exact computed result (structured query): SUM(revenue) = 4.2M across 4 rows (FY2024, all quarters)"

This lets Gemma cite the precise number instead of estimating it from retrieved prose. When nothing is recognized, this step is a silent no-op — the synthesis prompt is byte-identical to the ordinary path.

Query pipeline · Step 06

Synthesize the answer

The final chunks — numbered, labeled by store type, truncated to fit SYNTHESIS_CONTEXT_MAX_CHARS (12,000 chars) — are handed to Gemma 4 with a citation-aware system prompt. It returns strict JSON: answer (with inline [1]-style citations), confidence, sources_used, and notes.

Gemma's self-rated confidence rubric
BandMeaning
0.85 – 1.00Context directly and completely answers the query
0.65 – 0.84Mostly covered; some details inferred
0.40 – 0.64Only partial information available
< 0.40Context is largely irrelevant

The streaming endpoint (/query/stream) can't carry this JSON envelope alongside token deltas, so it streams the answer as plain text and issues one small follow-up grading call afterward against the completed answer — falling back to a retrieval-only confidence score if that call fails. If Gemma is unreachable at all, synthesis falls back to a plain concatenation of the top chunks with a retrieval-derived confidence, rather than failing the request.

All Gemma calls — synthesis, routing tier 3, RAVEN, SPYDER — share one pooled httpx client and a semaphore capped at GEMMA4_MAX_CONCURRENT (5 by default), so a burst of concurrent users queues gracefully instead of flooding the CDAC endpoint. Transient 429/5xx responses retry with exponential backoff (capped at 4s); a read timeout does not retry, since the model is already generating.

Optional layer · off by default

The agentic path: RAVEN → hybrid loop → SPYDER

When AGENTIC_RAG_ENABLED=True, steps 02–04 above are replaced by a bounded reasoning loop (agentic_pipeline.run()) instead of a single routing decision:

R

RAVEN reframes

A separate Gemma call cleans up the query, optionally splits it into up to 3 sub-questions, and may emit its own store_hint — a routing guess independent of intent_service.

↻

Bounded retrieve-and-judge loop

Fans out hybrid_retrieve() across the primary query and every sub-query, deduplicates, expands via the graph if available, then reranks. Runs at most AGENTIC_MAX_LOOPS (2) times.

S

SPYDER judges sufficiency

Asks Gemma whether the reranked chunks actually answer the query. Stops the loop on sufficient=true, confidence ≥ SPYDER_MIN_CONFIDENCE (0.6), or no better query to try; otherwise retries with SPYDER's reframed query. Fails open (assumes sufficient) on any error, so a Gemma outage can't cause an infinite loop.

Worth knowing

RAVEN's store_hint still lists image as a valid store name in its prompt, even though image_store has no embedding column and is never searched directly (image-derived content lives in the four searchable stores instead). Harmless in practice — get_handler()-style routing elsewhere already excludes it — but worth knowing if you're auditing RAVEN's raw output.

Worked example

Tracing one query through the router

Two queries through classify_intent(), showing where each one resolves.

"show me the revenue table for Q3"
Tier 1 — rules

_TABLE_KW matches "table" as the sole category hit → table only, confidence 0.85.

Gate

0.85 ≥ 0.80 → return immediately. Tiers 2 and 3 never run.

Result

Only table_store is searched. Zero wasted ANN queries against clause/research/vector.

"what did the firm bring in last quarter"
Tier 1 — rules

No literal match in any keyword list (no "revenue", "fiscal", "earnings"...) → ambiguous, all 4 stores, confidence 0.40.

Tier 2 — semantic router

The query embedding sits close to the table centroid ("what was the profit margin last fiscal year") with a wide margin over the rest → single store, confidence ≈ 0.85.

Gate

0.85 > 0.40 → semantic result wins over the ambiguous rule-based fallback.

Result

A paraphrase with zero shared keywords still routes to table_store alone — the improvement the semantic tier exists for.
