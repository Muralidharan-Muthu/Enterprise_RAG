Overview

One store, purpose-built for citation-bearing content

document_store is the PostgreSQL table (schema multi_store_rag_working) dedicated to research and scientific documents. Unlike the generic vector_store, it carries structural context — page number, section title, chunk type — and a schema-complete (if not yet fully populated) citation model, so retrieval can answer "what does the document say" with a page number and source attached, not just a similarity score.

Everything on this page is a single system: one PostgreSQL table, one ingestion write path, one retrieval read path. No other store or service is required for it to work end to end.

Multi-store routing

Where research documents land

Every ingested document is classified by the Gemma-4 router (with a rule-based fallback) into one of four types, each routed to a dedicated store. Only documents classified research are chunked into document_store.

Write path

Ingestion pipeline, step by step

Five stages, run once per uploaded document, tracked in ingestion_jobs.

1Parse & route
Docling
OCR + table extraction

Produces a ParsedDocument with raw text, page structure, and any tables/images.

Gemma 4 router
Document classification

Classifies document_type; falls back to rule-based classification if the endpoint is unavailable. Research-shaped content (abstract, methodology, citations) → document_type = 'research'.

2Chunk
Type-aware chunking

Chunker splits the document; each chunk retains its page_number and section_title for later citation.

3Embed
BGE embedding

Each chunk embedded at 1024 dimensions (bge-large-en-v1.5), the same model used for every store so cross-store similarity comparisons stay meaningful.

4Store
storage_service._store_research_chunks()

A single batched execute_values() INSERT writes every chunk of the document into document_store in one round trip (document_id, chunk_index, chunk_text, chunk_type, page_number, section_title, embedding, chunk_metadata), returning each row's generated id.

// storage_service.py — _store_research_chunks()
INSERT INTO multi_store_rag_working.document_store
    (document_id, chunk_index, chunk_text, chunk_type,
     page_number, section_title, embedding, chunk_metadata)
VALUES %s
RETURNING id
5Re-ingestion safety
Clear before re-insert

Re-ingesting the same document first deletes its prior document_store rows (alongside the other stores), so re-processing never leaves duplicate or stale chunks behind.

Read path

Retrieval pipeline, step by step

A query against document_store follows the same four-stage read path as every other store, so a research chunk and a policy chunk compete on equal footing by the time an answer is written.

1

Embed the query

The question is embedded with the BGE instruction prefix ("Represent this question for searching relevant passages: …") using the same 1024-dim model used at ingestion.

2

HNSW similarity search

_query_document_store() compares the query embedding against document_store.embedding via cosine distance (<=>), returning up to 15 candidates. Only chunks belonging to documents with document_registry.status = 'completed' are eligible, and results can be narrowed by document_types or a specific document_id.

3

Merge & rerank

document_store's candidates are merged with whatever other stores were searched, then the combined pool is reranked by a cross-encoder so relevance — not which store a chunk happened to live in — decides the final order.

4

Synthesize the answer

Gemma 4 writes the final answer from the reranked chunks, with citations built from each result's filename, page_number, and section_title.

Uniform result shape

Whatever store a chunk came from, its result row exposes the same columns — id, document_id, chunk_text, page_number, chunk_type, section_title, source_doi, filename, document_type, storage_path, storage_bucket — so downstream context-rendering and citation logic never needs to special-case document_store.

Full-text search

The generated chunk_text_tsv column lets document_store participate in keyword/hybrid search alongside vector similarity, for queries where exact term matching (a DOI, a model name, a specific number) matters more than semantic proximity.

By-id hydration

Given a set of document_store row ids, a dedicated by-id query returns the full chunk record in the same column shape as the similarity search — used when another part of the system already knows which rows it wants (e.g. the paginated chunk browser below) rather than needing to re-embed and re-search.

Worked example

"What is the Embedding Speed of Xeon 6787P with IPEX?"

A verified end-to-end retrieval test against Lenovo_Research.pdf, a document classified research and stored entirely in document_store — no other store or service involved.

38document_store rows for this PDF (chunk_index 0–37)
98%reported confidence
34.11send-to-end latency
What is the Embedding Speed of Xeon 6787P with IPEX?
Ingestion

Docling parsed the PDF; the router classified it research; the chunker produced 38 chunks, each embedded and inserted into document_store with its page_number and section_title intact.

Retrieval

The query was embedded and matched via HNSW cosine similarity against document_store rows, merged with the reranked pool, and answered by Gemma 4.

Answer

The system correctly returned 47 samples/sec (GTE model) and 133 samples/sec (MiniLM model) for Xeon 6787P with IPEX — matching the source chart in the PDF exactly — with a Research badge and citations to the correct source pages.

Data integrity: document_id is a NOT NULL foreign key with ON DELETE CASCADE — deleting a document_registry row removes its document_store chunks automatically. All access goes through the shared ThreadedConnectionPool (get_db() context manager); there is no ORM — schema changes are hand-written SQL applied manually via the Supabase SQL editor.
