Internal engineering reference

Chunks Become Entities, Queries Become Intent

Two separate Gemma 4 calls — one at ingestion, one per query — never talk to each other directly. They're connected only through canonical entity keys sitting in Neo4j. This is how that connection is built, and how a question decides whether to use it.

Overview

One graph, written by ingestion, read by queries

During ingestion, every chunk gets a second Gemma 4 pass whose only job is to pull out named entities and the relationships between them, which get merged into a Neo4j graph. During querying, the question itself gets the same entity-recognition treatment — not to extract a graph, but to check whether the graph already knows something relevant, and if so, to walk it instead of (or alongside) plain vector search.

The two lanes are asymmetric on purpose: ingestion always runs the graph extraction (when the flag is on), because it doesn't yet know what future questions will ask. Query-time is the opposite — it runs a cheap check first and only pays for a graph traversal (or a community map-reduce) when that check says it's worth it.

Phase 0 is two calls, not one

A dedicated Gemma 4 classifier (Phase 0a) runs before any entity extraction, deciding whether the question is genuinely about an entity's identity or relationships — as opposed to a factual/value lookup that merely mentions one. Only a "graph" verdict proceeds to Phase 0b (NER + Neo4j match). This exists because financial documents are graph-extracted too: a plain question like "What is the revenue of FY 2023-24?" names a fiscal period and a metric that can both exist as graph nodes, and the original single-step fuzzy match wrongly treated that as reason enough to traverse the graph. See Query understanding for the full prompt.

Ingestion

How a chunk becomes a node

Gated by GRAPHRAG_ENABLED and GRAPHRAG_EXTRACT_PER_CHUNK, every chunk — not just from research documents — gets one extra Gemma 4 call whose entire job is graph extraction, separate from the classification and synthesis calls elsewhere in the pipeline.

1

Prompt Gemma for entities and relationships in one call

The system prompt asks for two things from the chunk text: named entities (organisations, people, products, laws, concepts) and typed relationships between pairs of them — capped at the most salient N entities and M relationships, JSON only.

// graph_extraction_service.py — _GRAPH_SYSTEM_PROMPT (abbreviated)
{
  "entities": [
    {"name": "<exact surface form>", "type": "org|person|location|product|law|project|concept|misc",
     "description": "<one sentence>", "confidence": 0.0-1.0}
  ],
  "relationships": [
    {"source": "<entity name>", "target": "<entity name>",
     "type": "WORKS_AT | COMPARED_TO | APPLIES_TO | ...", "confidence": 0.0-1.0}
  ]
}
2

Parse tolerantly, degrade safely

Markdown fences are stripped and a regex fallback recovers JSON if the model wraps it in prose. If parsing still fails, the extractor falls back to entity-only NER (entity_service.extract_entities) with no relationships. This path never raises — a bad Gemma response costs entities for one chunk, not the ingestion job.

3

Canonicalize and merge entities

Each entity's surface name is canonicalized to a dedup key, then MERGE (e:Entity {key}) upserts it across every chunk and document that mentions it — the same person or product named slightly differently in two documents becomes one node. Every mention is traced back precisely:

// graph_service.py — one MENTIONED_IN edge per entity per document
MERGE (e:Entity {key: $key})
MERGE (e)-[m:MENTIONED_IN]->(d:Document {id: $doc_id})
// m carries: chunk_ids[], stores[], page_numbers[], confidence
4

Merge relationships as typed edges

Each relationship becomes MERGE (src)-[r:<TYPE>]->(tgt), with the edge label itself taken from Gemma's output (sanitized to a safe Cypher identifier; falls back to a generic RELATES_TO if the type is empty or unsafe). This is why the graph ends up with dozens of distinct relationship types — WORKS_AT, COMPARED_TO, APPLIED_TO, BASED_ON — rather than one generic edge.

5

Cluster into communities, periodically

A Louvain clustering pass groups densely-connected entities into Community nodes ((e)-[:IN_COMMUNITY]->(com)), and Gemma writes a prose summary of each cluster — the text that global-mode questions read later (see Decision). This doesn't run on every upload: it's gated so it only rebuilds when the graph is dirty and either 30 minutes have passed or 5 documents have queued up, keeping a large corpus from re-clustering on every single ingest.

Not just research documents

Graph extraction runs against whichever store a chunk landed in — GRAPHRAG_TABLE_STORE_ENABLED extracts entities from financial table rows (preferring their markdown rendering), and GRAPHRAG_IMAGE_STORE_ENABLED does the same for image captions/OCR text once it clears a minimum length. The graph is a cross-cutting layer over all four stores, not a fifth store of its own.

Query time

Two kinds of understanding, not one

It's tempting to think of "query understanding" as a single step. Multi-Store RAG Chatbot actually runs three independent Gemma 4 calls that answer three different questions, in a fixed order:

Phase 0a · first_is_entity_query()"Does this question WANT the entity graph, or is it a value lookup?"
Phase 0b · if "graph"route_graphrag() NER"Does this question name something the graph already knows?"
Phase 1 · alwaysRAVEN reframe"Which Postgres stores, and what sub-questions?"

Phase 0a — does this question even want the graph?

Before spending an entity-extraction call, a dedicated Gemma 4 classifier answers a narrower question first: is this genuinely about an entity's identity or relationships, or a plain factual/value lookup that merely happens to mention one? Only a "graph" verdict proceeds to Phase 0b below — everything else, including questions that name a fiscal period, product, or organisation, falls through to the cue-word check instead.

// graphrag_retriever.py — _ENTITY_INTENT_PROMPT (abbreviated)
Answer "graph" ONLY for identity/role or entity-relationship questions —
  e.g. "Who is <person>?", "How is <X> related to <Y>?"
Answer "search" for everything else — value/metric lookups, dates,
  counts, summaries — EVEN IF they mention a named period, product, or org.
  e.g. "What is the revenue of FY 2023-24 - Planned?" is "search".
Respond with ONLY JSON: {"mode": "graph" | "search"}
Why this exists

The original Phase 0 was a single fuzzy entity-match, no intent check: any noun phrase in the query that happened to fuzzy-match a graph node routed straight to local mode. Financial documents are graph-extracted too, so a plain value question like "What is the revenue of FY 2023-24?" named a fiscal period and a metric that both already existed as nodes — and got wrongly routed into local mode, dragging in unrelated graph chunks. The intent gate fixes this at the source: value lookups never reach entity extraction at all.

Phase 0b — which entity, and does it exist in the graph?

route_graphrag(query) then runs a Gemma NER pass over the raw question text — the same entity-extraction capability used at ingestion, just pointed at eight words instead of a chunk. Each extracted name is canonicalized and checked against Neo4j with a deliberately forgiving match:

// graphrag_retriever.py — fuzzy match against existing Entity.key nodes
MATCH (e:Entity) WHERE any(k IN $keys WHERE e.key CONTAINS k OR k CONTAINS e.key)
RETURN count(e) AS cnt

The CONTAINS-either-direction check exists because ingestion-time NER and query-time NER are two independent Gemma calls — they routinely phrase the same real-world entity slightly differently ("Kelvin He" vs "Kelvin He, AI Data Scientist"), and an exact-key match alone missed real hits.

Phase 1 — what's the intent, regardless of the graph?

RAVEN runs next (or in parallel in spirit, though sequential in code) and answers a completely separate question: reframe the query for retrieval, split it into up to three sub-queries, and produce a store_hint — the same policy/financial/legal/research intent classification used to pick which Postgres stores to search. This happens whether or not Phase 0 found a graph match; the graph is an addition to retrieval, not a replacement for deciding which stores matter.

The routing decision

Local, global, or none

Phase 0's output is exactly one of three modes, checked in this order:

Localgraph intent + entity found

Gemma says this is an entity question, and it matches the graph

Two gates must both pass: the Phase 0a intent classifier must answer "graph" (see Query understanding), and at least one extracted entity must fuzzy-match an existing Entity.key. Only then does local_neighborhood(entity_keys, hops=2) run its Cypher traversal — walking outward through typed relationship edges (never through MENTIONED_IN or IN_COMMUNITY, which aren't knowledge edges) up to the configured depth: direct mentions score 1.0, each further hop scores 1/(1+hop_distance) — 0.5 at hop 1, 0.33 at hop 2 (up to 3 hops supported) — genuinely crossing document boundaries wherever an entity is shared. Those chunks are hydrated with real text from Postgres and merged into the normal retrieval pool before reranking.

graph intent + entity match→local_neighborhood(hops=2)→chunks merged into pool, Graph +N badge
Globalnot local + cue word

Not eligible for local, but an aggregation or superlative cue

Reached whenever local doesn't fire — either Phase 0a said this isn't an entity/relationship question, or it is but no extracted entity matches the graph — and the query has a cue word from the aggregation/superlative set: originally words like compare, summarize, trend, extended this session with superlatives (highest, lowest, best, rank) so "find the X with the highest Y" routes here instead of falling through unanswered. A match selects the most relevant Community summaries, runs a Gemma MAP pass (one partial answer per community) and a REDUCE pass (final synthesis) — no chunk retrieval, no per-chunk citations, and no Graph badge in the UI (a citation-free community answer is no longer visually equated with a citation-backed local hit).

not local + cue word→community MAP → REDUCE→answer from graph alone, no badge
None

Neither — the graph is skipped entirely

No entity match and no cue word. The question falls through to ordinary hybrid retrieval (vector + keyword search) across whichever stores RAVEN's store_hint pointed to — Neo4j is never queried for this request, and no Graph badge appears.

All of this is best-effort: a Neo4j outage, a parse failure, or the graph flag being off all degrade silently to none — the classic vector/hybrid pipeline underneath never depends on the graph being available.

Worked example

"Who is Kelvin He and what is his role at Lenovo?"

A trace of a real question run against Lenovo_Research.pdf, verified end to end this session — from the entity extracted at ingestion through to the badge shown in the chat UI.

Who is Kelvin He and what is his role at Lenovo?
Ingestion — page 15

Gemma 4 read the author-bio chunk and extracted the relationship (Lenovo)-[:WORKS_AT]->(Kelvin He), confidence 1.0, description "Kelvin He is an AI Data Scientist at Lenovo." The edge carries page_numbers: [15] and the exact source chunk id.

Phase 0a — intent gate

"Who is X and what is his role at Y?" is squarely an identity/role question → Gemma answers "graph". Proceeds to Phase 0b (contrast the FY-2023-24 revenue example in the callout above, which the same gate answers "search").

Phase 0b — route_graphrag NER

Query-time NER extracts "Kelvin He" (and "Lenovo") from the question. Canonicalizing "Kelvin He" finds a matching Entity.key already sitting in Neo4j from the ingestion step above → mode = local.

Local search — hops=2

local_neighborhood() walks outward from the Kelvin He / Lenovo nodes and returns every chunk mentioning them directly or one hop away: 41 graph hits, hydrated into 6 real chunks not already found by hybrid search.

Retrieval + synthesis

The 6 graph-sourced chunks merge with the plain hybrid-search results, get reranked together by the cross-encoder, and Gemma 4 writes the final answer from the combined pool.

Response

The chat UI shows Research (the underlying document_store chunk) alongside Graph +6 (the six graph-contributed chunks), citing Lenovo_Research.pdf pages 1 and 15 — a one-to-one match back to the Neo4j edge extracted in step one.

Note on this trace

This trace predates the multi-hop depth fix: local_search() had a default-value bug (hops=1 combined with a dead hops or GRAPHRAG_LOCAL_HOPS fallback) that silently capped every live query at 1 hop regardless of the hops=2 shown in the code, so the "41 graph hits" above only ever explored hop 0 + hop 1. With the fix applied, the same question now genuinely reaches hop 2 as well and may surface additional, more indirectly-connected chunks.

Grounded in the codebase as of this session's GraphRAG debugging work. Confirmed bugs found and fixed, in the order they surfaced:

  1. The chat UI showed a Graph indicator for community (global) answers, not just entity-based (local) ones — badge logic now gates on graphMode === "local" only (frontend/src/app/query/page.tsx).
  2. The legacy multi-PDF expansion (graph_expanded_chunks) ran unconditionally, including for graph_mode == "none" — removed from the classic/streaming paths entirely; now runs only inside the agentic pipeline's local branch, additively (query.py, agents/agentic_pipeline.py).
  3. route_graphrag() over-triggered local mode on value/metric lookups that merely named an entity (e.g. a fiscal period) — added the Phase 0a Gemma intent gate, _is_entity_query(), described above (graphrag_retriever.py).
  4. extract_entities() misread a Gemma response that legitimately found zero entities as a parse failure (if parsed: instead of if parsed is not None:), which fell through to a noisy regex fallback that invented pseudo-entities from capitalized phrases like table headers — the same class of bug that fed spurious matches into bug 3 above (entity_service.py).
  5. Multi-hop depth was silently stuck at 1 instead of the configured 2: local_search()'s hops parameter defaulted to the truthy literal 1, making hops or settings.GRAPHRAG_LOCAL_HOPS dead code. Fixed to resolve from config via explicit is None checks — local mode now genuinely performs multi-hop, cross-document traversal at the configured depth (graphrag_retriever.py, retriever_service.py).
