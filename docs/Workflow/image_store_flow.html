Multi-Store RAG Chatbot · Multi-Store Pipeline

The Image Store, end to end

How a PDF's images are captured, understood and filed on upload — and how that knowledge reaches an answer when a user asks a question. Two flows, every branch and edge case included.

One idea to hold onto

The image_store is a permanent archive, not a search index. It keeps every image pulled from a document plus everything the system learned about it (OCR text, a vision-model reading, and a structured extraction). It has no embedding column — so it is never searched directly.

The moment an image is understood, its useful content is copied into the right destination store (tables, text, clauses or research) where it becomes searchable. Each of those copies carries a source_image_id pointer back to the original image. So routing happens once, at upload; search happens later, against the destination store.

Flow 1 · Upload

A PDF comes in

From the moment a file is uploaded to the moment every image is filed. Runs as a background job on the Celery worker; the UI shows the image count climbing live as rows are written.

1

Upload & fetch

The PDF lands in Supabase Storage. The worker downloads it to a temporary local file (keeping the real extension so the parser routes correctly), and deletes it when finished.

2

Parse with Docling

The document is parsed page by page (memory-bounded). Every embedded picture is pulled out with its page number, bbox (position on the page), width / height and the raw PNG bytes.

3

Pre-filter — cheap checks first

Each image runs a staged filter so expensive steps are only spent where they pay off. Order matters: throw away junk before paying for OCR, and OCR before paying for the vision model.

  • aTechnical filter (no OCR yet): drops tiny images (under 24 px or 1600 px²), blank/uniform ones, thin separator lines, and near-duplicates (perceptual hash).
  • bSurviving images are uploaded to storage at images/{doc}/{index}.png.
  • cOCR runs — only now, and only on images that passed step a.
  • dRule engine: small image + almost no text → logo/icon; low-information + faint → watermark. Both dropped.
  • eClassify the survivor: table, chart, diagram, screenshot, photo, text, or unknown.
  • fDecide the processing path (below).
Decision — three exits VLM_PROCESSED — table / chart / diagram / photo / unknown → send to vision model OCR_ONLY — plain text label → keep OCR, skip vision model SKIPPED — logo / icon / blank / duplicate → archived, not analysed
4

Vision model reads the image

Images marked for analysis go to the Gemma vision model, run in bounded parallel (capped worker threads, per-request timeout, OCR text trimmed to a max length so the prompt never overflows).

It returns a structured_content extraction (JSON), its own vlm_ocr_text transcription, a detected_store recommendation, and a confidence score.

If the model fails, times out, or returns bad JSON Fall back: route by raw OCR text instead — searchable text → text store, empty → stays an archived figure
5

Write the image_store row

One row is written per image — including the skipped ones, so nothing is lost and every decision is auditable. This row holds the picture's metadata and all three text readings, but no embedding.

📦 stored_in = NULL at this point. It only gets filled in once the content is actually copied into a destination store (next stage). A row that stays NULL is a pure figure living only in the archive.
6

Register table crops (lineage)

If the document had tables, each table's cropped image is filed in image_store first (tagged asset_role = table_crop) so its ID exists before the table row is written. That lets every table point back to the exact image it came from.

7

Route content into destination stores

For every image whose detected_store is not image_store, the system derives clean text from the extraction, embeds it in one batch (BGE, 1024-dim), and writes a row into the matching store:

table_store — for tabular images vector_store — general text clause_store — legal content document_store — research content
🔗 Each destination row is stamped from_image_store = TRUE and source_image_id = the archive row's ID. On success, the archive row's stored_in flips from NULL to that store. If the write fails, it stays NULL and the loop moves on — the image is never lost.

Edge cases handled — Flow 1

Tiny / blank / separator

Rejected before OCR. Archived with a skip reason, never analysed.

Duplicate image

Perceptual-hash match within tolerance → marked duplicate, skipped.

Logo / icon / watermark

Caught by the rule engine (small + little text, or low-info). Skipped.

PNG upload fails

That single image is dropped; the rest of the document continues.

OCR fails

Fails open to empty text; the image still goes to the vision model.

Vision model times out / bad JSON

Falls back to routing by raw OCR text. No crash, no data loss.

Plain text label (OCR-only)

Skips the vision model; routed by its text — to the text store if searchable, else archived.

Image is really a table

Extraction routed to table_store; archive row's stored_in set to table_store.

Pure figure, no text

Stays in the archive only. stored_in remains NULL — retrievable by lineage, not by search.

Document re-processed

All prior image_store rows for that document are deleted first — a clean slate, no duplicates.

Flow 2 · Question

A user asks something

How image-derived knowledge reaches the answer. Remember the core idea: the archive itself is never searched — the search hits the destination store the image's content was copied into at upload.

Why there is no "search the image_store" step

Because the useful content already lives in a searchable store (with an embedding) by the time any question is asked. A query about a chart or figure is steered toward the table_store and vector_store — exactly where image-derived rows were filed. The source_image_id link back to the original picture exists for traceability; it is not walked during search.

1

Query arrives

The user's question hits the query API with options like document filters and result count.

2

Conversational gate

Greetings and small talk are answered directly — retrieval is skipped entirely for anything that isn't a real information request.

3

Intent classification — pick the stores

The query is read for intent. Visual words like chart, figure, image, diagram steer the search toward the tables and text stores where image content lives.

Visual query routes to table_store vector_store image_store is never in the search set
4

Embed the query

The question is embedded with the same BGE model used at upload (with a search-instruction prefix), so it lands in the same 1024-dim space as the stored content.

5

Vector search the destination stores

An HNSW nearest-neighbour search runs across the selected stores — vector, clause, research, table — concurrently. Image-derived rows (from_image_store = TRUE) compete here alongside native text on equal terms.

6

Hybrid keyword fusion

When enabled, a full-text keyword search runs in parallel and the two ranked lists are blended (reciprocal-rank fusion). The archive has no keyword index, so it sits this out too.

7

Graph expansion

If the knowledge graph is available, related documents pull in a few extra chunks. Purely additive — a no-op when the graph is offline, and it never touches the archive.

8

Balance & rerank

Results are capped per store so no single source dominates, then a BGE cross-encoder reranker scores each candidate against the exact question and keeps the strongest.

9

Synthesise the answer

The top chunks — including any image-derived ones — are assembled into a context budget and sent to Gemma, which writes a cited answer with a confidence score. The text used is the destination store's copy of the image content.

✅ The user gets an answer grounded in a chart or table that originally lived as an image — without the retriever ever having to open the archive.

Edge cases handled — Flow 2

Non-visual question

Intent routes to text/clause/research stores; image-derived table rows simply don't surface.

Answer comes from a former image

Served as an ordinary table/text row — the user sees the content, lineage is recorded underneath.

Lineage exists but isn't traversed

source_image_id links a row to its origin image but is not followed during search — it's for audit/trace.

No matches

"No image match" can't happen — images aren't searched. Only the destination stores can come back empty.

The two jobs the image_store does

JOB 1

Permanent, auditable archive

Every image ever extracted is kept — with its OCR, vision reading, classification and the reason behind every filter decision. Nothing is silently dropped.

JOB 2

Lineage anchor

Any answer chunk that came from a picture can be traced straight back to that picture via source_image_id — proof of where a number or fact originated.
