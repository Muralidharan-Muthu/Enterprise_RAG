01 Overview

Multi-Store RAG Chatbot's table pipeline turns tables inside a PDF into data that is queryable, retrievable, and exactly computable. Schema: multi_store_rag_working. All behaviour below is verified against a live Docker stack (API + Celery worker + Supabase/pgvector), not just unit-tested.

A table can be: extracted whole from one page (common); split across pages by Docling and merged back into one logical table; extracted with rowspan/colspan/multi-row headers captured as a structural span map; and queried two ways at once — semantically (embeddings) and exactly (a structured aggregate engine).

Figure 1 — Overall architecture: ingestion → multi-store Postgres → dual-path query.

02 Ingestion Pipeline

Twelve stages, PDF only. Parsing is page-chunked (bounded memory, live progress) with a whole-document Docling fallback and a PyMuPDF last resort.

Figure 2 — Full ingestion pipeline, colour-coded by concern.
Why page-chunked parsingDocling loads a 1.3 GB model set; converting a huge PDF whole-document risks unbounded memory. _adaptive_chunk_size() keeps ≤8 pages in flight and yields ~25–40 live progress updates. Trade-off: it converts small docs (≤25 pages) one page at a time — which is why multi-page tables split and need re-merging.

_adaptive_chunk_size — document_parser.py:668show ▾
def _adaptive_chunk_size(total_pages: int) -> int:
    # 5p→1, 50p→2, 200p→8, 1000p→8 : ≤8 pages in flight
    if total_pages <= 1:
        return 1
    return max(1, min(8, math.ceil(total_pages / 25)))

03 Multi-page Continuation

Docling emits one table object per physical page-appearance. _merge_continued_tables() stitches consecutive-page fragments with identical headers back into one logical table before storage.

Figure 3 — Three page-fragments → one merged table with per-row page provenance.

Merge rule (exact)

Tables sorted by (page_number, table_index). Adjacent A→B merge iff all three hold: (1) B.page_number == A.page_number + 1, (2) A.headers == B.headers exactly, (3) every row length equals len(headers). Greedy left-to-right, transitive.

What a merge produces

  • rows = concatenation in page order; row_page_numbers = per-row origin page (new ExtractedTable field, None for unmerged — full back-compat).
  • page_number, bbox, image_png_bytes = first fragment's (representative). One crop image per logical table, not per fragment.
  • table_metadata["continuation"] = {is_continuation, fragment_count, fragment_pages, fragment_table_indices}. Unmerged tables get no such key.
  • table_index renumbered contiguously; span map keeps only the first fragment's (page-local offsets can't concatenate).
Accepted false positiveTwo unrelated tables with identical headers on strictly consecutive pages will merge — no semantic-dissimilarity guard. Deliberate simplicity trade-off. Continuation is PDF-only (not wired into DOCX/PPTX/XLSX/HTML/MD).

04 Per-cell Span Model

_detect_merged_cells() reads Docling's raw table.data.table_cells — not the dense grid, which duplicates a spanned cell's text into every covered position and always reports uniform widths. This was the key finding that unlocked genuine span detection.

Figure 4 — Span geometry captured; multi-row header combined into single column labels.
Why this fixed a real bugPreviously only grid row 0 was treated as the header. A genuine 2-row header silently misclassified its second row as a data row — corrupting row_count and leaking header fragments into searchable text. Now detected via Docling's own column_header flag, never by row-content heuristics.

Docling attrs verified (docling-core 2.74.0): row_span, col_span, start/end_row_offset_idx (0-based, exclusive), column_header: bool. Format gap: DOCX/PPTX/XLSX/MD backends never set column_header → header_row_count stays 0 for those.

05 VLM Reconciliation & Faithfulness Gate

table_reconstruction.py re-runs the multimodal VLM on each crop, then decides Docling-vs-VLM via a three-tier numeric-faithfulness gate that rejects hallucinated numbers.

Docling gridMerged cells?Tolerance for VLM-introduced unseen numbers
Well-formed (uniform)No0% — any unseen number rejects the VLM
Well-formedYes8% _MERGED_CELL_TOLERANCE — merged grids look uniform but are structurally richer
Raggedeither20% _FAITHFULNESS_TOLERANCE — no reliable native structure
Signal sourcehas_merged_cells comes from table_metadata.merged_cells.has_merged_cells, fail-open to false if absent — so the span model (§4) directly drives which tolerance tier a table gets.

06 Lineage Flow

Every stored row traces back to its PDF origin. Image, table, and chunk lineage are all 1:1 or clean 1:many — verified live end-to-end, hop by hop.

Figure 5 — PDF → merged table → crop image (1:1) + chunks (1:many) → embeddings → citation.

Key relationship: table_store.source_image_id → image_store.id, unique 1:1, asset_role='table_crop'. Because merging happens upstream in the parser, exactly one crop exists per logical table.

08 Retrieval Pipeline

Two parallel, independently-gated paths per query — never mutually exclusive. Semantic (embeddings, multi-window) and structured (exact aggregate) both run; results feed one synthesis prompt.

Figure 7 — Dual-path retrieval converging on one synthesis prompt.

Multi-window: deduped per table_id to the top-K closest windows (TABLE_MAX_WINDOWS_PER_QUERY_RESULT, default 2). Generic to table_id — needed no change for continuation-merged tables. _resolve_chunk_page_range() reads chunk_metadata.page_start/end defensively → RetrievedChunk.page_number_end (null for single-page).

09 Structured Query Engine

Deterministic, non-LLM, rule-based exact aggregation. Additive: returns None when no aggregate intent → semantic path byte-for-byte unchanged. Gated by STRUCTURED_QUERY_ENABLED.

Figure 8 — SUM over a continuation-merged table sums all pages' rows for free (json_data is per-logical-table).
Known gaps (follow-up, non-blocking)(1) _extract_target_column's verbatim-substring fast path can false-positive on plurals ("months" matches a "Month" column). Fix: word-boundary match. (2) /query/stream with AGENTIC_RAG_ENABLED=True (non-default) never reaches the structured call. (3) Single-table only — no cross-table aggregate.

10 Worker Lifecycle & Identity

worker_identity.py stamps worker_id + code_version into every job so any divergence between worker processes/versions is diagnosable from the DB alone.

Figure 9 — Worker identity stamped at first status update, wrapped so a pre-migration env never fails ingestion.
Why it exists — a real incidentA stray native Celery worker running stale code shared the Redis queue with the Docker worker. Task delivery is nondeterministic per-task, so identical re-ingestions silently alternated between correct (merged) and broken (unmerged) output — both reporting completed, no distinguishing signal. Stamping + the count-mismatch gate (§11) together close this: a mismatch is caught before completed, and the error names the responsible worker/version. Note: the Docker worker image has no git binary, so code_version='unknown' today — a correct, non-fatal degradation.

14 Known Limitations

Accepted, documented trade-offs — not oversights.

  • Span model is span-only — geometry + text per region, but nothing downstream reconstructs a visual table yet (exists for the faithfulness gate + future use).
  • Continuation false positives — unrelated tables with identical headers on consecutive pages merge; no semantic guard.
  • PDF-only continuation — _parse_non_pdf never calls _merge_continued_tables.
  • column_header gap — DOCX/PPTX/XLSX/MD backends never set it → header_row_count always 0 for those.
  • Structured engine is single-table — no cross-table aggregate.
  • Column-match substring false-positive (plurals) — follow-up, not fixed.
  • Agentic-streaming + structured gap — non-default config only.
  • Synthesis-quality gaps — downstream of Gemma, not the table pipeline.
